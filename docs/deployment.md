# Installation and deployment

## Local development

Install Node.js 24 LTS (minimum supported version 22.12) and use either a local MongoDB service or Atlas. Run all npm commands from the repository root, not the older sibling project.

```powershell
cd 'C:\Akshat\bolt flowboard\Flowboard2\flowboard-mern'
npm.cmd ci
npm.cmd run setup
npm.cmd run dev
```

On macOS/Linux use `npm` instead of `npm.cmd`. Setup creates missing `server/.env` and `client/.env` files, generates a JWT secret, and preserves existing files. Configure MongoDB before starting. Open `http://localhost:5173`; keep the terminal running. The API is `http://127.0.0.1:4001/api/health`. `/api/ready` must also return 200 before testing authenticated features.

Separate terminals may run `npm run dev -w server` and `npm run dev -w client`. The API watcher watches server and shared source. No server compilation is needed. No container runtime or TypeScript compiler is required.

## Environment reference

Server values are private and loaded from `server/.env`, relative to the module rather than the working directory. Hosting-platform environment variables take precedence.

- `NODE_ENV`: `development`, `test`, or `production`. Default development. Production changes cookie security and enables frontend serving by default.
- `PORT`: integer 1–65535; default `4001`.
- `HOST`: listen address; default `127.0.0.1`. Keep loopback when a local reverse proxy fronts Express. Use the provider's required private interface or `0.0.0.0` only when its network controls prevent direct public bypass of the proxy.
- `MONGODB_URI`: required private MongoDB connection string, including the intended database. Atlas URIs begin `mongodb+srv://`; local URIs begin `mongodb://`. The runtime does not use `DATABASE_URL`.
- `CLIENT_ORIGIN`: required exact browser origin, such as `http://localhost:5173` locally or `https://flowboard.example.com` in production. No path or trailing slash. Production requires HTTPS.
- `JWT_SECRET`: required random value of at least 48 characters. Use the secret generated by setup or a secret manager. Rotation invalidates every existing session.
- `TRUST_PROXY`: empty by default. Comma-separated trusted proxy IP addresses/CIDRs or `loopback`. For a local nginx proxy use `loopback`. Blanket `true`, numeric hop counts and hostnames are rejected. Use only the actual proxy network; a broadly trusted network permits spoofed client IPs.
- `SERVE_CLIENT`: optional literal `true` or `false`. Default true in production and false otherwise. When true, startup requires `client/dist/index.html` and serves the built frontend, deep links and assets.

Client values:

- `VITE_API_URL`: public build-time API base, normally `/api`. Keep the same origin for the production topology below. Never put passwords, database URLs or session secrets in any `VITE_*` value.
- `API_PROXY_TARGET`: development-only Vite target, normally `http://127.0.0.1:4001`; it is not shipped in browser code.
- `SMOKE_PORT`: optional environment variable for `npm run smoke`, default 4002. This is a test utility setting, not a server deployment variable.

Restart Node after server environment changes; rebuild after client build-time changes. Use the same hostname consistently: `localhost` and `127.0.0.1` have separate cookies/origins.

## Production: one application process behind HTTPS

This is the supported initial deployment topology. It requires a working DNS name, valid TLS certificate, Node process manager/service, MongoDB credentials restricted to the intended database, and network access between the host and MongoDB. These external resources are not provisioned by the repository.

1. Deploy a clean checkout plus the lockfile to a versioned release directory.
2. Install build/test dependencies and run the checks:

   ```sh
   npm ci
   npm run check
   npm run format:check
   npm test
   npm run build
   ```

3. Provision `server/.env` securely or inject environment variables. Example values below are placeholders:

   ```dotenv
   NODE_ENV=production
   HOST=127.0.0.1
   PORT=4001
   CLIENT_ORIGIN=https://flowboard.example.com
   MONGODB_URI=mongodb+srv://DATABASE_USER:ENCODED_PASSWORD@YOUR_CLUSTER/flowboardmern
   JWT_SECRET=REPLACE_WITH_A_RANDOM_SECRET_USING_NPM_RUN_SETUP
   TRUST_PROXY=loopback
   SERVE_CLIENT=true
   ```

4. Start `npm start` under the host's service manager, with the repository root as its working directory. Run as an unprivileged account. Keep secrets out of shell history and source control. Use a reasonable automatic restart policy and capture stderr/stdout.
5. Terminate TLS at a reverse proxy and forward all paths, including Socket.IO upgrades, to Express. The following nginx fragment assumes nginx and Node run on the same machine. Substitute the domain and real certificate paths; validate with `nginx -t` before reload.

   ```nginx
   # Place map in the http context.
   map $http_upgrade $connection_upgrade {
       default upgrade;
       ''      close;
   }

   server {
       listen 80;
       server_name flowboard.example.com;
       return 301 https://$host$request_uri;
   }

   server {
       listen 443 ssl;
       server_name flowboard.example.com;
       ssl_certificate     /etc/letsencrypt/live/flowboard.example.com/fullchain.pem;
       ssl_certificate_key /etc/letsencrypt/live/flowboard.example.com/privkey.pem;
       client_max_body_size 64k;

       location / {
           proxy_pass http://127.0.0.1:4001;
           proxy_http_version 1.1;
           proxy_set_header Host $host;
           proxy_set_header X-Forwarded-Proto $scheme;
           # A single edge proxy overwrites untrusted incoming forwarding headers.
           proxy_set_header X-Forwarded-For $remote_addr;
           proxy_set_header Upgrade $http_upgrade;
           proxy_set_header Connection $connection_upgrade;
           proxy_read_timeout 75s;
       }
   }
   ```

6. Verify `/api/health` and `/api/ready`, register a designated test account, sign in, confirm Secure/HttpOnly/SameSite cookie attributes, create and move a card, refresh a deep link, and verify two-tab live updates and logout. Test that another account cannot read the first account's board.
7. Enable monitoring for readiness failures, authentication throttles and HTTP 5xx. Use platform access logs with credential/cookie redaction. No application request body or secret should enter logs.

Express serves only `client/dist`. Hashed assets under `assets/` have one-year immutable caching; HTML uses `no-cache`; API responses use `no-store`. Missing API routes and missing assets return errors instead of an HTML fallback. Google Fonts is no longer needed; fonts are local system fonts. Vite's dev/preview server is not a production service.

## Database operations and rollback

- Back up before deployment and regularly thereafter, using Atlas backups or your managed MongoDB backup process. Verify a restore into a separate database; backup existence alone is not evidence of recovery.
- Startup waits for unique email and board-list indexes. Existing duplicate emails must be resolved deliberately before the unique index can build. Do not silently delete accounts.
- The new board-list index adds `_id` for deterministic order. An older `{owner, updatedAt}` index may remain in an existing database. This audit deliberately does not drop indexes; after measuring, a DBA can remove an obsolete redundant index during maintenance.
- No user documents need migration for this audit. Existing IDs, owners, password hashes and embedded board/card relationships are preserved. Earlier local data is not copied to Atlas.
- Roll back by switching the service to the previous release and retaining the same secrets/database. No destructive schema migration is included. Before rollback, check compatibility with any later schema changes.
- Board/column/card deletion is permanent in the current product. Use backups for recovery; a future trash/history feature is a separate product change.

## Capacity boundaries

Start with one Node instance. Both the authentication limiter and Socket.IO adapter use process-local state. Before running multiple instances, implement a shared limiter store and Socket.IO adapter, coordinate session revocation across instances, and configure sticky sessions if polling remains enabled. Test those changes explicitly; simply adding instances does not preserve current guarantees.

Board documents are bounded to 30 columns/500 cards. Dashboard pages default to 24 summaries and cap at 100. Page counting and offset pagination are adequate for a small private workspace; load-test realistic volumes before increasing limits. For very large datasets, evaluate cursor pagination and separate card collections with transactions.

## Common operational failures

- **Connection refused:** the process is stopped or listening on a different host/port. Start the documented command, inspect startup logs, then check readiness.
- **MongoDB startup failure/503:** verify URI encoding, database user permissions, Atlas network allowlist, DNS and connectivity. Production credentials must not use the example placeholder.
- **CORS/403:** exact origin mismatch or missing `X-Flowboard-Request`. Do not solve this by enabling every origin.
- **Login fails over HTTP in production:** Secure cookies require HTTPS. Keep production secure; use development mode for local HTTP.
- **429 for many unrelated users:** verify proxy allowlist and overwritten forwarding headers before raising rate limits.
- **408 in the UI:** the 15-second client deadline expired. Refresh before retrying a create; it may have committed despite a lost response.
- **409 while editing:** another tab changed the board. Preserve your text, cancel/reopen the editor and reapply the intended change.
- **Live sync unavailable:** inspect `/socket.io` proxy upgrades, cookies, readiness and session expiry. REST refresh remains available.
- **Client build missing:** run `npm run build` before enabling `SERVE_CLIENT`.
- **EADDRINUSE:** identify the process already bound to the intended port; do not kill every Node process.

Real public HTTPS, DNS, proxy installation, host hardening, backup restoration and load testing remain deployment acceptance steps; local tests do not certify them.
